# eCatalog AZ — подробная схема работы платформы и гибкий план развития

## 1) Цель продукта

Создать единую платформу, которая объединяет:
- агрегатор цен (сравнение предложений магазинов),
- маркетплейс объявлений (новые и б/у товары),
- инструменты доверия и безопасности сделки,
- модуль аналитики (для покупателей, продавцов и админ-команды).

Ключевая идея: **одна карточка товара = много предложений** (магазины + частные продавцы), где пользователь сразу видит оптимальный вариант по цене, состоянию, доставке и надежности продавца.

---

## 2) Бизнес-сущности (единая модель данных)

Чтобы система была гибкой, нужно отделить "товар как модель" от "конкретного предложения".

### 2.1 Основные сущности

1. **CatalogProduct** (каталожная модель)
   - `id`
   - `category_id`
   - `brand_id`
   - `model_name` (например, "iPhone 13 128GB")
   - `normalized_specs` (JSON: память, цвет, диагональ и т.д.)
   - `status` (`active`, `archived`)

2. **Offer** (конкретное предложение)
   - `id`
   - `product_id`
   - `seller_id`
   - `condition` (`new`, `used`, `refurbished`)
   - `price`, `currency`
   - `stock_status` (`in_stock`, `out_of_stock`, `preorder`)
   - `city`, `delivery_options`
   - `warranty_months`
   - `created_at`, `updated_at`

3. **Seller**
   - `id`
   - `type` (`shop`, `private`)
   - `name`
   - `verification_level`
   - `rating`, `review_count`
   - `risk_score`

4. **Category / AttributeSchema**
   - задают какие характеристики обязательны в каждой категории,
   - позволяют добавлять новые категории без переписывания кода.

5. **PriceHistory**
   - хранит изменение цены по `offer_id` во времени,
   - используется для графика и уведомлений "цена снизилась".

6. **ModerationCase / FraudSignal**
   - жалобы, автосигналы подозрений, решения модераторов.

### 2.2 Почему это гибко

- Можно добавлять новые форматы продавцов (дилеры, дропшип) без изменения ядра.
- Можно расширять атрибуты категорий через схемы, а не миграции при каждом поле.
- Б/у и новые товары работают в едином поиске, но с разными правилами качества.

## 3) Функциональная схема работы платформы (end-to-end)

## 3.1 Поток данных от источников

1. Источник данных:
   - API магазина,
   - XML/CSV фид,
   - кабинет продавца (ручное размещение),
   - аккуратный парсер (если нет API),
   - SEO JSON-LD extraction (Product/Offer) как стандартный fallback для сайтов без API.

2. Ingestion Service принимает сырой поток и сохраняет в `raw_offers`.

3. Normalization Service:
   - чистит названия,
   - извлекает бренд/модель/атрибуты,
   - приводит единицы измерения к стандарту.

4. Matching Service:
   - связывает raw-offer с существующим `CatalogProduct`,
   - либо создает кандидат на новую модель,
   - отправляет сомнительные совпадения на ручную проверку.

5. Offer Upsert Service:
   - обновляет/создает `Offer`,
   - пишет изменение цены в `PriceHistory`,
   - запускает переиндексацию поиска.

6. Quality & Fraud Service:
   - проверка аномально низкой/высокой цены,
   - поиск дублей объявлений,
   - выявление подозрительного поведения аккаунта.

## 3.2 Поток пользователя (покупателя)

1. Пользователь открывает каталог → Search API отдает результаты из поискового индекса.
2. Фильтрует по состоянию (`new/used`), цене, городу, рейтингу продавца.
3. На карточке товара видит:
   - все предложения,
   - историю цен,
   - блок "проверенные продавцы",
   - похожие товары.
4. Пользователь:
   - переходит в магазин по реферальной ссылке,
   - или пишет частному продавцу,
   - или откладывает товар в watchlist.
5. Notification Service отправляет alert при падении цены / появлении нужного б/у варианта.

## 3.3 Поток продавца

1. Регистрация и верификация (телефон, документы для магазинов).
2. Публикация оффера:
   - обязательные поля по категории,
   - фото-валидация,
   - состояние товара + дефекты для б/у.
3. Модерация (авто + ручная).
4. После публикации продавец видит аналитику: просмотры, конверсия, конкурентные цены.

## 4) Логическая архитектура сервисов

### 4.1 Сервисы уровня платформы

- **API Gateway / BFF**
  - единая точка входа для Web/Mobile,
  - auth, rate-limit, A/B флаги.

- **Catalog Service**
  - карточки моделей, категории, характеристики.

- **Offer Service**
  - предложения продавцов, наличие, цена, доставка.

- **Search Service**
  - полнотекст + фильтры + сортировки.

- **Ingestion Service**
  - импорт от магазинов и внешних источников.

- **Matching & Normalization Service**
  - нормализация атрибутов и дедупликация.

- **Moderation/Fraud Service**
  - риск-модели, кейсы модерации, санкции.

- **Notification Service**
  - email, push, Telegram/WhatsApp (при необходимости).

- **User & Identity Service**
  - аккаунты, роли, верификация.

- **Analytics Service**
  - BI-метрики, отчеты продавцам, продуктовая аналитика.

### 4.2 Слои хранения

- **PostgreSQL**: транзакционные данные (товары, офферы, пользователи).
- **Elasticsearch/Meilisearch**: быстрый поиск и агрегации.
- **Redis**: кэш, сессии, очереди задач.
- **Object Storage (S3)**: изображения товаров и артефакты модерации.
- **Data Warehouse (опционально позже)**: долгосрочная аналитика и ML.

### 4.3 Событийная шина

Рекомендуется event-driven подход:
- `offer.updated`
- `price.changed`
- `seller.verified`
- `fraud.signal.created`

Это снижает связанность и позволяет легко подключать новые функции (например, динамическое ценообразование) без переписывания монолита.

## 5) Архитектура интерфейса (Web + Admin)

## 5.1 Пользовательский фронт

Разделы:
- Главная (популярные категории, тренды цен),
- Каталог + фильтры,
- Карточка товара,
- ЛК покупателя (watchlist, сравнение),
- ЛК продавца.

UI-паттерны:
- "Compare drawer" для сравнения нескольких моделей,
- "Best offer" бейдж с прозрачным расчетом,
- график истории цены,
- отдельные бейджи состояния: Новый / Б.У. / Refurbished.

## 5.2 Админ-панель

Модули:
- очередь модерации,
- управление категориями и атрибутами,
- контроль интеграций (фиды, ошибки импорта),
- антифрод-дашборд,
- управление рекламными слотами и промо.

---

## 6) Нефункциональные требования (чтобы платформа не "сломалась" на росте)

1. **Производительность**
   - p95 поиска < 400ms,
   - p95 карточки < 600ms,
   - кэш топ-страниц и агрегатов.

2. **Надежность**
   - retries + DLQ для ingestion pipeline,
   - SLA на ключевые сервисы,
   - ежедневные бэкапы и тест восстановления.

3. **Безопасность**
   - RBAC по ролям,
   - защита от брутфорса/спама,
   - аудит действий модераторов,
   - шифрование чувствительных данных.

4. **Наблюдаемость**
   - централизованные логи,
   - трассировка запросов,
   - алерты по бизнес-метрикам (резкий рост фрода, падение конверсии).

5. **Локализация**
   - AZ/RU/EN,
   - форматы валют/дат,
   - региональные правила доставки.

## 7) Гибкий roadmap (с проверкой на расширяемость)

Ниже план с "точками гибкости", чтобы безболезненно добавлять функции.

## Phase 0 — Foundation (2–4 недели)

**Что делаем:**
- Базовая доменная модель (CatalogProduct/Offer/Seller),
- API Gateway + auth,
- базовый Search индекс,
- CI/CD, мониторинг, feature flags.

**Гибкость:**
- Сразу вводим event schema и versioning API,
- контрактные тесты между сервисами.

## Phase 1 — MVP Core (4–8 недель)

**Что делаем:**
- Каталог, карточка, фильтры, сравнение,
- кабинет продавца,
- импорт из 5–10 источников,
- базовая модерация.

**Гибкость:**
- подключение новых источников по adapter-интерфейсу,
- расширяемые category schemas (JSON schema/metadata-driven forms).

## Phase 2 — Trust & Retention (6–10 недель)

**Что делаем:**
- рейтинги и отзывы,
- история цен и алерты,
- антифрод v1,
- верификация магазинов.

**Гибкость:**
- risk engine как отдельный сервис,
- правила фрода конфигурируемые (не зашитые в код).

## Phase 3 — Monetization & Scale (8–12 недель)

**Что делаем:**
- рекламные форматы,
- платные промо-объявления,
- BI-кабинет для продавцов,
- A/B эксперименты.

**Гибкость:**
- billing module выделен отдельно,
- единая система entitlements/тарифов для будущих B2B-продуктов.

## Phase 4 — Intelligent Platform (дальше)

**Что делаем:**
- персональные рекомендации,
- прогноз цены,
- авто-матчинг похожих б/у объявлений,
- anti-fraud ML v2.

**Гибкость:**
- feature store/warehouse готовятся заранее,
- model serving через отдельный inference слой.

## 8) Проверка плана на "максимальную гибкость" (чеклист)

План считается гибким, если соблюдены пункты:

1. **Schema evolution**
   - есть миграции + обратная совместимость,
   - новые атрибуты добавляются через метаданные.

2. **API evolution**
   - версионирование (`/v1`, `/v2`) или header-version,
   - deprecated-поля удаляются только после grace period.

3. **Event evolution**
   - каждое событие имеет версию,
   - потребители устойчивы к неизвестным полям.

4. **Integration plug-in model**
   - каждый источник реализует единый adapter contract,
   - падение одного адаптера не ломает ingestion целиком.

5. **Deployment flexibility**
   - canary/blue-green,
   - rollback без миграционных катастроф.

6. **Business flexibility**
   - правила комиссий/рекламы вынесены в конфиг/админку,
   - сегментация пользователей без переписывания ядра.

7. **Geo & language flexibility**
   - multi-language контентная модель,
   - региональные налоги/доставка подключаются как policy modules.

## 9) Риски и как заранее снизить

1. **Плохое качество данных от источников**
   - внедрить data quality score и quarantine-поток.

2. **Сложный matching одинаковых товаров**
   - гибрид: правила + ML + ручная валидация edge-cases.

3. **Фейковые б/у объявления**
   - обязательные фото/видео, лимиты на публикацию, риск-скоринг.

4. **Рост стоимости инфраструктуры**
   - tiered storage, кэширование hot-path, архивирование старых данных.

5. **Юридические/комплаенс вопросы**
   - прозрачная политика модерации, хранение логов действий, consent flows.

## 10) KPI для контроля успеха

- Search CTR,
- Conversion to click/contact,
- Доля "чистых" офферов после модерации,
- Time-to-publish для продавца,
- % успешного matching,
- Fraud incident rate,
- Retention 30/90,
- ARPU/B2B revenue per seller.

---

## 11) Рекомендуемый стартовый tech stack

- Frontend: Next.js + TypeScript,
- Backend: NestJS/FastAPI (service-oriented),
- DB: PostgreSQL,
- Search: Elasticsearch или Meilisearch,
- Queue/Event Bus: Kafka/RabbitMQ,
- Cache: Redis,
- Storage: S3-compatible,
- Observability: Prometheus + Grafana + OpenTelemetry,
- CI/CD: GitHub Actions/GitLab CI.

Главное: выбирать стек не "по моде", а по способности команды поддерживать его 2–3 года.
